皆さんこんにちは。React習熟度シリーズの15記事目です。前回の記事では、Opus 5のReact習熟度ベンチマークのスコアがFable 5を大きく上回るという衝撃の展開がありました。そのため、Opus 5はFable 5より進んだ世代のモデルではないかと目されていました。そのため、Fable 5.1の結果がどうなるかに注目が集まっていました（N=1）。

ということで、今回は先日公開された**Claude Fable 5.1**のReact習熟度ベンチマーク結果をお伝えします。

なお、いつもeffort=highとeffort=maxの結果をお届けてしますが、この記事はひとまずhighだけです。その理由は、maxだととんでもなく時間がかかりそうで、その間Claudeを使用できなくなってしまうのが困るからです。そのうちmaxの結果もお届けしたいと思います。

## 結果

まず順位表です。

Fable 5.1 (effort=high)は、Fable 5 (effort=max)とほぼ同スコアで、Opus 5 (effort=high)に迫る結果となりました。

差は小さく、この結果は**Fable 5.1がOpus 5に追いついた**と解釈してよいでしょう。

今回興味深いのはカテゴリ別スコアです。

コンポーネント設計・アクセシビリティのスコアが伸びており、Fable 5 (effort=max)やOpus 5 (effort=high)を超える結果となっています。アクセシビリティに関しては、従来世代よりも `aria-describedby` や `aria-live` の活用が大幅に増加したことが報告されています。

一方で、パフォーマンス意識はFable 5から変わっておらず、最上位層に差をつけられています。

## 考察

このベンチマークはOpus 5の時点でサチっているようでしたが、Fable 5.1に対してベンチマークを走らせる意味がありました。Fable 5.1はOpus 5と同程度で、Fable 5からの進化が明確になったからです。

王者がOpus 5 (effort=max) であることは変わっていません。そのため、Fable 5.1がOpus 5を超えたというわけではなく、あくまで同程度になった、ということが分かる結果となっています。

Fable 5.1をeffort=maxで走らせたらここを超えられるのかは楽しみですが、とんでもなくusageを消費するので結果をお届けできるのは先になりそうです。

## 3. a11y の +0.67 はコードのどこに出たか

カテゴリ点は評価者モデルの判断なので、実装コードを直接数えて裏を取った。アーカイブ単位の出現率（Fable 5: 42ディレクトリ / Fable 5.1: 43ディレクトリ）。

| 属性 | Fable 5 | **Fable 5.1** |
|---|---:|---:|
| `aria-describedby` | 1 | **14** |
| `aria-live` | 6 | **23** |
| `role=` | 34 | 39 |
| `useId` | **0** | **12** |

`role` はもともとほぼ全実装が書いていた（つまり「ARIA を書く」ことは前世代でもできていた）。変わったのは中身のほうで、**入力とエラーメッセージを結ぶ `aria-describedby` が 1 → 14、非同期の状態変化を読み上げに流す `aria-live` が 6 → 23**。どちらも「マークアップに role を足す」より一段実務的な作業である。

`useId` の 0 → 12 も同じ流れに属する。ラベルと説明を id で結ぶには安定した一意 id が要る、という順序で必要になるフックで、**a11y をやろうとした結果としてモダン API が1つ増えた**という筋書きが素直に読める。

## 6. 本回最大の発見: スペック 008 はそもそもコンパイルできない

3サンプルすべてで 008 が `compiles: false` になった。3/3 は偶然ではないので原因を追った。**結論から言うと、モデルの落ち度ではなくベンチマークの欠陥である。**

**事実1.** `specs/008-form-actions/data-model.ts:35` はこう宣言している。

```ts
export async function submitSurvey(data: SurveyData): Promise<SubmissionResult> {
  await new Promise((r) => setTimeout(r, 1000 + Math.random() * 1000));
  if (Math.random() < 0.3) { ... }
```

擬似サーバなので `data` は本文で一度も読まれない。

**事実2.** `scaffold/tsconfig.json` は `"noUnusedParameters": true` を立てている。したがって**この提供ファイルは単体で `tsc` を通らない**（`TS6133: 'data' is declared but its value is never read.`）。

**事実3.** 実装プロンプト（`runner/run.ts:673`）はこう指示している。

> The data model types are already at src/data-model.ts — import from there. **Do not modify data-model.ts.**
> - **Make sure the code compiles with TypeScript.**

この2つは 008 では**同時に満たせない**。

**検証。** アーカイブを再構築して確かめた。Opus 5 max の 008 を復元して `tsc -b --noEmit` → 通る。Sonnet 5 の 008 を同じ手順で復元 → `TS6133` で落ちる。両者の `data-model.ts` は**バイト単位で同一**（md5 一致）。差分は `tsconfig.json` の一行だった。Opus 5 max 側にはご丁寧に理由まで書き添えてある。

```
// The provided (unmodifiable) data-model.ts declares a `data` parameter it
// never reads, which this check rejects.
"noUnusedParameters": false,
```

つまり **008 を「コンパイル成功」にする道は2本しかない**。プロジェクトの型チェック設定を緩めるか、「変更するな」と言われたファイルを書き換えるか（Haiku は後者を選び、`data` を `_data` にリネームしていた）。

**歴代への影響。** 008 の採点済み実行 54件のうち **19件が非コンパイル**。しかもモデル別の内訳は tsconfig を触ったかどうかとほぼ完全に一致する。

| tsconfig を緩めた | 008 の非コンパイル |
|---|---|
| GPT-5.6 全6条件、Fable 5、Fable 5 max | 0 |
| Sonnet 5、Opus 4.8、Opus 4.7、**Fable 5.1** | 各 3/3 |

そして本ベンチ全史で記録された非コンパイル 22件のうち、**19件が 008 である**（残りは 003、007、013 が各1件）。

**Fable 5.1 は3サンプルすべてで tsconfig を出荷時のまま残した。** 3/39 という非コンパイル数字は、コードが壊れていたのではなく、**言われた制約を守った結果**である。

**スコアへの影響はない。** `compiles` は `weighted_score` の計算に入らず、`evaluation/rubric.md` はコンパイルに一言も触れていない。判定はコードそのものに対して行われる。**86.44 はこの件の影響を受けていない。**

影響を受けるのは信頼性の指標のほうだ。第1〜14回が「非コンパイル N/39」として並べてきた数字は、実際には**プロジェクトの型チェック設定を緩める意思があるかどうか**を大部分で測っていた。順位の解釈を変えるほどではないが、あの列を「実装の堅さ」として読むのはもうやめたほうがいい。

## 8. 信頼性

39実装すべてが完走し、判定不能はゼロ。非コンパイル 3件はすべて 008 で、内容は §6 のとおり。使用制限による待機は複数回発生し、うち1回は9時間規模になったが、`--retry-on-limit` がそのまま吸収し、失われたスペックはない（待機明けは早期復帰プローブが拾った）。

## 9. effort=max を中断したこと

max 条件は high の3サンプル完走直後（2026-09-03 05:53 JST）に開始し、同日中に使用量の都合で**意図的に停止した**。得られたのは s1 の3スペックのみで、条件としては成立していない。

| スペック | max (n=1) | high (n=3 平均) |
|---|---:|---:|
| 001 | 98 | 95.3 |
| 002 | 95 | 89.0 |
| 003 | 90 | 83.7 |

3スペックとも high を上回ってはいる。**が、これは結論として扱えない。** 第14回で Opus 5 max の1本目だけを見て「006 が解けた」と早合点しかけ、2本目（74点）に否定された前例がそのまま当てはまる。この表は「続きを走らせる価値がある」以上のことを主張しない。

部分スコアは `scores/multi_fable-5.1-max-s1_2026-09-02.json` に残してある。`--resume` を指定すれば済んだ3スペックを飛ばして続行できる。

## 10. 注意書き

- 評価者は `sonnet-4.6` ピンのまま、`--effort` を渡さない呼び出しも第1回から不変。実装側は `effort: "high"` 明示ピン（41becf1 の方針）。
- v1 スキャフォールドの二重 React 欠陥（`docs/audit-2026-07-26.md` §5.1）は未修正のまま。Fable 5.1 も他条件と同じ環境を踏んでいるので比較可能性は保たれている。修正は v2 較正前に行うべきで、v1 の途中で直せば過去回との比較が壊れる。
- v1 の飽和は進行している。今回も 012 が3回とも96、011 が3回とも90、TypeScript品質は 4.92。上位帯の識別力はほぼ残っていない。

## 11. 次にやること

1. **008 のデータモデルを修正する**（v2 で）。`data` を実際に使うか `_data` にする。今のままだと「設定を緩める意思」を測ってしまう。同時に、`compiles` を信頼性指標として報告するのをやめるか、意味を再定義する。
2. **二重 React 欠陥の修正**と Playwright スモークゲートの前倒し（監査 §5.1 の提案）。008 の件と合わせて、**v1 の自動チェックはコンパイルしか見ておらず、そのコンパイルが測っている対象も怪しかった**ことになる。v2 のゲート設計はここを踏まえる必要がある。
3. **Fable 5.1 の effort=max を n=3 で走らせる**。使用量に余裕のあるときに。high が前世代 max に並んだ以上、max がどこまで伸びるか（あるいは Opus 5 max の 90.28 に届くか）は v1 で測れる最後の面白い問いかもしれない。
4. **010 ツリーエクスプローラの分析**。全モデルが落とし続けている唯一のスペックで、今回は世代内で唯一の後退でもあった。v2 の難所設計の参考になる。
