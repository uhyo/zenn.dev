## 考察

Opus 5はこのベンチマークをクリアしたのかもしれません。

このベンチマークで最強だったFable 5を圧倒し、Opus 5が新しいReact習熟度トップに立ちました。

まず、Opus 5のレベルになってくると、effortの恩恵は限定的になってくるようです。従来Claude系モデルではeffortをhighからmaxに上げるとスコアが4～5点上がっていましたが、Opus 5では3点程度しか上がっていません。

また、スペックごとのスコアを見ると、highがスコアでmaxを上回っている場面もあり、highとmaxの差が運によるノイズに隠れてしまうようです。

ただし、特定のスペックではmaxがhighを大きく上回る場面があります（スペック004, 006, 010）。特に004と006は難しいスペックであり、Opus 5がそこでしっかりと得点してきたことは注目に値します。逆に、ここを攻略されるとこれ以上のモデルの進化をこのベンチマークで測るのは難しそうです。

カテゴリ別スコアを見ると、Opus 5は特にコンポーネント設計とアクセシビリティでスコアが伸びています。アクセシビリティに関しては、アクセシビリティを得意としていたGPT-5.6 Solと同程度のスコアを叩きだしており、Claudeの弱点を消す動きです。

この結果を見ると、Opus 5はReact開発においては最強のモデルといって差し支えないでしょう。（ClaudeとGPT系しかベンチマーク取っていないので、他に密かな最強モデルがいたらすみません）。ちなみに、コスパもそんな悪くないように見えます。effort=highとeffort=maxのベンチマークをMaxサブスクで土日のうちに走り切れました。

ちなみに、これだけのスコアを出してもなお、React 19以降の新しいAPIの使いこなしはまだまだ筆者の期待する水準には達していません。ただ、Opus 5はReact 19.2で登場した`useEffectEvent`を初めて自主的に使用したモデルになっており、着実に進歩しています。

以下の生レポートにもありますが、今後のモデルの進化に対応できるようにインフレさせたベンチマークv2を計画中です。引き続きよろしくお願いします。

# 第14回: Opus 5 — 天井に頭がぶつかった日

**実施日**: 2026年7月25〜26日
**評価対象**: Claude **Opus 5**、effort=high と effort=max（どちらも新規、各 n=3）
**評価者モデル**: Claude Sonnet 4.6（`sonnet-4.6` にピン留め。第1回から不変）
**スペック数**: 13 / **総実装数**: 78

---

今回は新モデルの計測と、ベンチマーク自身の限界の露呈が同時に起きた回である。数字から入る。

| 条件 | 総合（n=3） | サンプル別 | 非コンパイル |
|---|---:|---|---:|
| Opus 5 **high** | **87.00** | 87.15 / 86.85 / 87.00 | 1/39 |
| Opus 5 **max** | **90.28** | 91.46 / 89.00 / 90.38 | 0/39 |

max は本ベンチ初の 90 台。そして high の 87.00 が、第10回から立っていた記録（Fable 5 max の 86.67）をすでに抜いている。**新世代の high が、前世代最強の max を上回った**——今回いちばん端的な事実はこれだ。

## 1. effort 曲線が平らになった

面白いのは記録の更新そのものより、その内訳である。上位モデルの effort 一段（high→max）あたりの伸びを並べるとこうなる。

| モデル | high | max | Δ |
|---|---:|---:|---:|
| Opus 4.8 | 79.38 | 84.03 | +4.65 |
| Fable 5 | 81.33 | 86.67 | +5.34 |
| **Opus 5** | **87.00** | **90.28** | **+3.28** |

Opus 5 は**上位3モデルの中で effort の伸びしろが最も小さい**。第13回で Fable の effort 曲線（low 74.6 / high 81.3 / max 86.7、一段あたり約 +6）を「effort に強く依存するモデル」と書いたが、Opus 5 はその逆を向いている。

これは弱点ではなく、むしろ質の移動と読むべきだ。**以前は max を焚かなければ届かなかった水準に、high の時点で届いている。** 実務的な含意はわかりやすい——Fable では「効かせないと元が取れない」が結論だったのに対し、Opus 5 では **high が既に十分に強く、max は 3 点強の上積みを買うオプション**にすぎない。使用量を考えれば、常用は high でよく、max は後述する「難所スペック」に賭けたいときの手段になる。

## 2. ただし max は「安定して良い」わけではない

サンプル別の数字をもう一度見てほしい。high は 87.15 / 86.85 / 87.00——**13スペック×3周してブレ幅 0.30**。このベンチでは異常な安定度である（スペック単位では従来 ±10〜15 振れるのが常だった）。ところが max は 91.46 / 89.00 / 90.38 とブレ幅 2.46 に広がる。スペック単位で見るともっとはっきりする。

| 条件 | スペックあたりの振れ幅（3サンプルの最大−最小、平均） | 最大 |
|---|---:|---:|
| high | 5.9 | 11 |
| max | 10.0 | **25** |

振れ幅 25 の犯人は 006 通知フィード（99 / 74 / 90）で、004 プロフィール閲覧（100 / 78 / 81）がそれに次ぐ。どちらも**歴代モデルが軒並み落としてきた難所**である。

つまり max がやっているのは、平均の底上げというより**難所での分布の押し広げ**だ。うまくいった回は 99 や 100 を叩き出し、外した回は high と同水準に落ちる。期待値は上がるが、当たり外れも大きくなる。「max にすれば安定して良くなる」ではなく、「max にすると**上振れの目が出る**」と表現するのが正確で、n=1 の観測で max を語ると景色が変わってしまう理由でもある（実際、私も max の1本目だけを見て「006 が解けた」と早合点しかけた）。

## 3. カテゴリ: 世代の跳躍はアクセシビリティと設計に出た

| カテゴリ | Opus 4.8 high | Opus 5 high | Opus 5 max | 世代差（high） |
|---|---:|---:|---:|---:|
| 状態設計 | 4.56 | **4.92** | 4.87 | +0.36 |
| Effect衛生 | 4.10 | 4.38 | **4.54** | +0.28 |
| コンポーネント設計 | 3.67 | 4.23 | **4.49** | +0.56 |
| TypeScript品質 | 4.82 | 4.87 | 4.85 | +0.05 |
| パフォーマンス意識 | 3.67 | 4.00 | **4.21** | +0.33 |
| **アクセシビリティ** | 3.59 | **4.31** | **4.62** | **+0.72** |

一世代で最も動いたのは **a11y（+0.72）** である。Opus 4.8 の 3.59 は、GPT-5.6 各層（3.79〜4.54）に明確に負けていた項目で、第11・12回では「Claude の弱点、OpenAI 勢の強み」と書いた領域だった。Opus 5 max の 4.62 はその GPT-5.6 の最高値（Sol max 4.54）を上回り、**この一年続いていた構図がひっくり返った**。

コンポーネント設計 4.49 も本ベンチの全条件で最高値である（従来最高は Fable 5 max と Opus 5 high の 4.23）。GPT-5.6 が 2.90〜3.38 に留まっていた項目で、ここは依然として差が大きい。

一方で**パフォーマンス意識（4.00 / 4.21）は相変わらず全カテゴリ中の最下位**だ。どのモデル・どの世代でも最後まで残るのがこの項目で、Opus 5 も例外ではない。次節がその中身の話になる。

## 4. モダン React API: 書きぶりは今も React 18 世代

第12回で GPT-5.6 について調べた「実際にどの API を使っているか」を、同じやり方で Opus 5 にも当てた（実装アーカイブのディレクトリ単位で出現を数えたもの。リトライ分を含むため母数は 39 より少し多い）。

| API | Opus 5 high (41) | Opus 5 max (43) | 参考: Opus 4.8 high (42) |
|---|---:|---:|---:|
| `useTransition` | 0 | 1 | 0 |
| `startTransition` | 0 | 1 | 0 |
| `useOptimistic` | 0 | 1 | 0 |
| `useActionState` | 3 | 3 | 1 |
| `useEffectEvent` | 0 | **3** | 0 |
| `useDeferredValue` | 3 | 3 | 3 |
| `useMemo` | 28 (68%) | 27 (63%) | 24 (57%) |
| `memo(...)` | 7 | 13 | 4 |

スコアが 90 に乗ったモデルとしては、この表はかなり地味である。

- **並行機能はほぼ使われていない。** `useTransition` は 78 実装中 1 本、`useOptimistic` も 1 本。第12回で GPT-5.6 について「React 18 世代の書き方」と評したが、**Opus 5 も同じ穴に落ちている**。重い更新を優先度で分ける発想が、コードにほとんど現れない。パフォーマンス意識が伸びない実体はここにある。
- **`useEffectEvent` が初めて現れた。** 本ベンチで観測されたのは今回が最初（max で 3 本）。React 19.2 で安定化した比較的新しい API で、`useOptimistic` の 1 本と合わせ、**「最新 API を知ってはいるが、まだ手が伸びていない」**段階に見える。
- **手動メモ化はむしろ増えている。** `useMemo` が 6 割強、`memo()` が max で 13 本。Opus 4.8（57% / 4本）より積極的だ。v1 のルーブリックはこれを咎めないが、**v2 の scaffold は React Compiler を有効にしてある**ので、同じ書きぶりは「コンパイラを信用せず手で抱え込んでいる」と評価される側に回る。今回いちばん v2 で数字が動きそうな箇所である。

## 6. 信頼性

max は **39本すべてコンパイル成功**。high は 008 フォームアクションで1本落ちた（Fable 5 low でも同じスペックで1本落ちている）。

ただしその 008 の非コンパイル run は、**コンパイルが通らないまま 89 点**で採点されている。v1 は型エラーを減点しないので、こういう本が平均に混ざる。v2 で `tsc` 失敗を ×0.6 のゲートにする、というのはまさにこの穴を塞ぐ話であり、今回もその必要性を1本ぶん再確認した格好になる。

## 8. 注意書き

- **筆者と被験体が同じである。** この回の対象は Opus 5 で、このレポートを書いているのも Opus 5 である。採点者は Sonnet 4.6 に固定されており、自己採点は発生していない——しかし解釈の書き手が中立でないことは記しておく。数値と生成物はすべて `scores/` と `results/` にあるので、読み手が自分で検算できる。
- **effort=high は従来「デフォルト」と呼んでいたもの**である（7月17日にレジストリで明示ピン留め済み、commit 41becf1）。過去回の「デフォルト」の数字とそのまま比較してよい。
- API 使用率の母数はアーカイブのディレクトリ数で、リトライ分を含むため 39 ちょうどではない。傾向を見る用途に限る。

## 9. 次にやること

1. **v2 への移行を本気で進める。** 今回で v1 の頭打ちは論証された。特に「モダン API を使わずに手動メモ化する」という Opus 5 の実像は、v1 のスコア 90.28 からはまったく読み取れない。React Compiler を有効にした v2 scaffold と expert 帯のチェックポイントは、この乖離を数字にするために設計されている。
2. **Opus 5 の低 effort。** high と max の差が +3.28 しかないなら、low はどこまで落ちるのか。Fable は low で −6.72 と大きく崩れた（第13回）。「良いモデルほど effort 依存が小さい」という仮説が立つので、これは検証する価値がある。
3. **難所スペックでの max の分散。** 006 が 99 / 74 / 90 と割れた原因は、n=3 では特定できない。同一スペックを反復して分布そのものを見る実験が要る。
