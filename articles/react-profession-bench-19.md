## 考察

GPT-5.6の時点ではSolとLunaがスコアで競うという不思議な現象を見せていたGPTですが、6系になり明暗が分かれました。Solは6.1で順当に進化し、GPT-6 Astraと同程度までReact習熟度を伸ばしています。一方、GPT-6 Lunaは5.6の時点よりもスコアが下がり、Solとの差がとても明白になりました。Lunaは安さにより特化したモデルと位置づけられたのかもしれません。

スコアの内訳に関しても、これまでのGPTシリーズと同じ傾向が続いています。GPT-5.6の時点からGPTのモデルは同世代のClaudeに対してアクセシビリティが強い傾向を示していましたが、GPT-6.1でもその傾向を維持し続けています。

コンポーネント設計の雑さでClaudeの上位モデルに差をつけられている状況ですから、この癖が直れば一気にClaudeに追いつくかもしれません。

## 7. 非コンパイル列の読み方（再掲）

今回 Sol は high/max ともに 0/39、Luna も 0/39、Astra max は 2/39 だった。**これを堅牢性の指標として読んではいけない。**

全履歴の非コンパイル36件のうち**33件がスペック008**であり（残り3件は 003 / 007 / 013 に各1件）、原因は `specs/008-form-actions/data-model.ts` が未使用の `data` 引数を宣言している一方で `scaffold/tsconfig.json` が `noUnusedParameters: true` を設定している点にある。プロンプトは「data-model.ts を変更するな」と「TypeScript がコンパイルできることを確認せよ」を同時に要求しており、両立しない。逃げ道は tsconfig を緩めるか「変更禁止」のファイルを編集するかの二択である。

したがってこの列が実際に測っているのは、**プロジェクトの型チェック設定を勝手に緩める意思があるかどうか**である。制約に従うモデル（Opus 5.5 max は 3/39）が非コンパイルとして記録され、設定を緩めるモデル（OpenAI 系のほぼ全ティア）が 0/39 になる。今回 Astra max だけ 2/39 を出しているのは、OpenAI 系でも常に緩めるとは限らないことを示している。`compiles` は `weighted_score` に寄与しないため順位には影響しない。v2 でデータモデル側を修正する（`docs/benchmark-v2-plan.md`）。

## 8. 交絡: codex CLI のバージョンが、世代と完全に相関している

今回いちばん重要な方法論上の発見である。

| codex CLI | インストール | その CLI で測った条件 |
|---|---|---|
| 0.144.4 | 2026-07-15 00:34 UTC | GPT-5.6 Luna / Terra / Sol（high・max、7月15〜17日） |
| 0.153.4 | 2026-09-09 13:26 UTC | GPT-6 Astra（high・max、9月9日〜10月5日） |
| 0.160.0 | 2026-10-05 17:30 UTC | GPT-6.1 Sol / GPT-6 Luna（high・max、10月5〜9日） |

各世代の最初の実装は、対応する CLI のインストールから **27分後 / 6分後 / 1分後** に始まっている。理由は単純で、**新モデルを動かすには新しい CLI が必要**だからである（0.153.4 では `gpt-6.1-sol` と `gpt-6-luna` のスラッグが未知で、サーバが打ち間違いと同じ 400 を返す）。

結果として、本ベンチの codex 系では **CLI バージョンとモデル世代が完全に相関している**。これは次を意味する:

- §2 の「GPT-6 Luna は GPT-5.6 Luna より低い（−5.31）」は、**「0.160.0 は 0.144.4 より低いコードを書かせる」と区別できない。** CLI はツールループ・プロンプト整形・サンドボックス方針を持っており、生成物に影響しうる。
- §3 の「GPT-6 世代は effort の伸びが倍」も同様に、CLI 側の変化で説明できる可能性が残る。
- Claude 系の条件は**この交絡を持たない**が、それは CLI がピン留めされているからではない。`claude` CLI も同様に未固定・未記録であり、ただ世代と一対一に相関する理由がないだけである（新しい Claude モデルは既存の CLI で動くので、CLI 更新と新モデル投入のタイミングが揃わない）。つまり Claude 側にあるのは「交絡」ではなく「**記録されていない変数**」である。

さらに言えば、**ピン留めした評価者を動かしているのも、その未固定の `claude` CLI である。** 第1回から変えていないのは評価者の*モデル*（`sonnet-4.6`）と `getEvaluationArgs` の引数であって、判定を実行するバイナリのバージョンは一度も固定していない。

実装側 CLI も一度もピン留めしておらず、スコアファイルに記録もしてこなかった（行の中身は `spec` / `model` / `timestamp` / `compiles` / `weighted_score` / `categories` / `error` だけ）。第16回以前の報告でもこの点に触れていなかった。

これは「過去のスコアが間違っている」という話ではない。各条件は内部的には単一 CLI で一貫して測られており（世代とバージョンの切れ目が揃っているので、条件をまたぐ混在はない）、スコアそのものは有効である。問題は**世代間の差分を読むとき**に、モデルの差と CLI の差を分離できないことである。
