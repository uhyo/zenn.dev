## 考察

まず、high同士の比較では、Haiku 5.5がSonnet 5.5を上回ってしまったことは注目に値します。一方で、Sonnet 5.5とは大きく異なる点として、Haiku 5.5はeffortを上げても効果は限定的なようでした。

そもそも、Haiku 5.5のほうがSonnet 5.5よりも2倍以上の時間をかけて実装していたのが不思議ですね。この点がHaiku 5.5のスコアを押し上げたのかもしれません。もしかしたら、両者は単なる性能の良し悪しがあるだけでなく、異なる役割を持つモデルとして作られているのかもしれませんね。

カテゴリ別スコアに関しては、Claudeのモデル同士では特定のカテゴリが得意・苦手ということがあまりなく、全体的に連動しながら上下しがちなので、そこまで特筆すべきことがある感じではありません。総合スコアが十分に実力を反映していると言えるでしょう。

いずれにせよ、Opus, Sonnet, Haikuと5.5世代が出てきましたが、いずれも高いレベルでまとまっています。同世代のGPT（GPT-6やGPT-6.1）との性能比較ではClaude側に分がある結果となりました。OpusとSolの比較もさることながら、下位モデルのHaikuとLunaを比較しても差がついています。

上位の 006 と 005 は、どちらも Effect 衛生の重みが 30% のスペックである（`evaluation/<spec>/expected-signals.json`）。そしてそこで起きたことは、ソースを数えれば確認できる。

| 要求される API | Haiku high | Haiku max | Sonnet high | Sonnet max |
|---|---:|---:|---:|---:|
| 006: `useEffectEvent` | 0/3 | **3/3** | 0/3 | 1/3 |
| 005: `useSyncExternalStore` | 3/3 | 3/3 | 3/3 | 3/3 |

006 は単純で、max になって初めて `useEffectEvent` を使った。Sonnet 5.5 max ですら 1/3 なので、この点に限れば Haiku max のほうが確実だ。

005 はもっと面白い。high でも `useSyncExternalStore` は3回とも使っている。違いは**網羅性**で、high は5つある外部購読のうち4つを `useSyncExternalStore` にし、毎回どれか1つ（イベントバス、viewport、イベントバス）を `useEffect + useState` のまま残した。判定理由は3回とも「5つのうち4つは正しい」で始まる。max は全部を変換し、`useEffect` は正当な2つ（イベントバスの起動/停止と `setInterval`）だけになった。

> Only two `useEffect` calls exist in the entire codebase … Every browser API subscription — online/offline, resize, matchMedia (×2), visibilitychange, and the event bus — is handled via `useSyncExternalStore`
> （Haiku 5.5 max, 005, s2）

逆に、max でも変わらなかったものがある。

- **コンポーネント設計とパフォーマンス**は high→max で 4.18 → 4.15、3.90 → 3.79。動いていない。
- **009 の −6.00** は、両 effort とも同じ失点（`PendingButton` が `useTransition` ではなく `useState` で pending を手管理）を重ねた結果であり、max 固有の後退ではない。high 79–90、max 75–84 とサンプル範囲は重なっている。なお 009 で `useTransition` を使った実装は、今回確認した5条件（Haiku 5.5 ×2、Sonnet 5.5 ×2、Opus 5.5 max）で 0 件だった。

これは第19回の分析ドキュメント（`docs/analysis-2026-10-09.md` §4）の結論をそのまま裏づける。**Effect 衛生カテゴリは「特定の React 19 API を使ったか」を採点しており、effort の上げ下げはそこに直接効く。** 古典的な意味での Effect 衛生（クリーンアップ、依存配列、派生値）は Haiku でもすでに飽和している。

## 5. 非コンパイル（再掲）

両条件とも 3/39 で、6件すべてがスペック 008 である。全履歴では 42件中39件が 008 になった。008 は `data-model.ts` 自体が `noUnusedParameters` に違反しているため、「指定ファイルを変更しない」という制約を守るモデルほど非コンパイルとして記録される。**この列は堅牢性ではなく、tsconfig を緩める意思の有無を測っている。** `weighted_score` には入らないので順位に影響はない。

## 6. harness: 判定理由が消えていた

### 何が起きていたか

`run.ts` は、スコア行（`scores/*.json`）は採点のたびに書き込む一方で、評価者の判定全文（`results/<run>/evaluation-result.json`）は**プロセスが正常終了したときにまとめて**書いていた。`run-samples.sh` のウォッチドッグがホストのスリープ後に `run.ts` を stall-kill すると、そのパスで採点済みだった全スペックの判定理由がディスクに残らない。スコアは無事なので、これまで誰も気づかなかった。

今回は max の s1 と s2 でそれぞれ1回 stall-kill が起きた（10月9日 21:59、10月10日 13:34 JST、どちらもホストのスリープ）。その結果、s1 は 11件、s2 は 2件の判定理由を失っている。kill されたスペック自体（s1 の 012、s2 の 003）は次のパスで最初からやり直されているので、スコアは正しい。

### どこまで遡るか

採点済み行数と判定理由ファイル数を条件ごとに突き合わせた。

| 条件 | 採点済み | 判定理由あり | 欠落 |
|---|---:|---:|---:|
| GPT-6 Astra max | 39 | 8 | **31** |
| Haiku 5.5 max | 39 | 26 | 13 |
| Fable 5 | 39 | 27 | 12 |
| Opus 5 | 39 | 27 | 12 |
| Opus 5.5 max | 39 | 28 | 11 |
| GPT-6.1 Sol max | 39 | 31 | 8 |
| GPT-6 Astra high | 39 | 32 | 7 |
| Opus 4.8 max | 39 | 35 | 4 |

合計で約100件。過去のスコア・順位にはまったく影響しない。影響するのは判定理由の本文を読む分析だけで、`docs/analysis-2026-10-09.md` §2・§4 の理由文の集計は、**Astra max の理由文をほとんど含んでいない**（8/39）。同ドキュメントの付録に注記を加えた。

### 修正

判定結果が返った時点で、スコア行の upsert と同じ場所で `evaluation-result.json` を書くようにした（`runner/run.ts` の `archiveEvaluation`）。終了時のまとめ書きは削除した。採点経路は1本しかないので、これで全実行が対象になる。

### 運用記録

- high は 3時間3分で完走（10月9日 12:12 → 15:15 JST）。中断なし。
- max は 30時間42分。実装1件あたり約17分かかることに加えて、上記のスリープによる停止が2回入った（s1 で約3時間、s2 で約14時間。どちらも90分の無出力検知を含む）。使用量上限には一度も当たっていない。
- 判定 JSON のエスケープ修復が1回（max s1 の 010）。自動回復済み。
- モデル ID の検証: `claude-haiku-5-5` は本物の ID としてそのまま応答し、架空の ID（`claude-haiku-5-5-bogus`）は拒否された。effort が実際に効いていることも確認した（固定の算数問題で思考トークンが low 178 / high 244 / max 728）。
- 応答したモデル名は、第1回以来どの条件でも記録していない（スコア行にも、`--no-session-persistence` のため CLI のトランスクリプトにも残らない）。これは Haiku 5.5 に固有の問題ではなく、全条件が同じ間接的な根拠に立っている。今回の根拠は、本番と同じ `--model claude-haiku-5-5` で本物のモデルが応答したこと、架空の ID が別モデルに差し替えられず拒否されたこと、high と max で実装時間が8倍違うこと。結果が誤りであるには、有効な ID に対してサーバ側が別モデルを返していた必要があり、そう疑う材料はない。

## 8. この結果から言えないこと

- **「Haiku 5.5 は Sonnet 5.5 より優れている」とは言えない。** 言えるのは high 同士の比較だけで、その差は Sonnet 側の作業量の少なさでほぼ説明できる（§2）。max 同士では Sonnet が 6.2 点上。
- **Haiku 4.5 → 5.5 の伸び幅は測れていない。** 4.5 は n=1 で、CLI も effort の扱いも違う。
- **effort の効果 +1.74 は、3スペックの API 採否でほぼ決まっている。** v1 の Effect 衛生カテゴリが API 採否を採点している以上、この数字は「Haiku は深く考えても設計が良くならない」と「v1 は設計の改善を拾いにくい」のどちらとも読める。区別するには v2 で API 採否を独立の軸に分ける必要がある（`docs/analysis-2026-10-09.md` §6.1）。
- 評価者は Sonnet 4.6 のままで、Haiku 5.5 の出力を自社の旧モデルが採点している。これは全条件に共通の前提であり、Haiku 5.5 だけに有利・不利が生じる仕組みは見当たらない。
